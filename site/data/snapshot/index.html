Genesis snapshot — and how to check it yourself

Eligibility was decided once, from the on-chain state at snapshot block B = 50,615,795 — the block in which the token was deployed. Everything needed to reproduce that decision is published here. You are not asked to trust it; you are asked to re-run it.

1. Check the set root

Recompute the Merkle root from the list and compare it with what the contract stores. If these differ, the published list is not the committed one.

python3 lottery/build_v2_proofs.py --addresses site/data/snapshot/eligible.txt --out /tmp/check --limit 1
cast call 0x292198f6aceb505EbaD96ba7654bAe70B57c0fdd "setRoot()(bytes32)" \
  --rpc-url https://base-rpc.publicnode.com

Run every command on this page from the repository root. --limit 1 computes the root over the whole list but writes only one proof file.

2. Check the candidate universe

The header binds candidates_keccak = keccak256 of the candidate file's bytes. The hash takes 15–20 minutes because keccak.py is deliberately pure Python; the byte count is a free pre-check.

gh release download snapshot-b50615795 -p candidates.txt.gz -R second-btc/second-bitcoin
gunzip -c candidates.txt.gz > candidates.txt
python3 -c "import sys;sys.path.insert(0,'lottery');from keccak import keccak256;\
print('0x'+keccak256(open('candidates.txt','rb').read()).hex())"   # == header.json candidates_keccak

You do not have to trust this file either: §2 of the eligibility spec defines the candidate set as the senders of the window's blocks, so it is re-derivable from any archive node.

3. Re-run the whole rule

The strongest check. This re-derives the block anchors from T_B, refuses a header whose parameters differ from the verifier's own constants, re-reads every consensus value from archive nodes with no derived shortcuts, and exits non-zero on any mismatch.

BASE_RPC_URL=<base archive> ETH_RPC_URL=<eth archive> \
python3 lottery/snapshot_v2.py verify \
    --header site/data/snapshot/header.json --candidates candidates.txt \
    --expect-root 0x40586f19308707d4dd2f4db69416ad385f2d5b07ab7c616ae9aae1ac21c69390 \
    --expect-n 84089

4. …and that the candidate universe was complete

What step 3 does not cover. verify accepts the candidate file as given — candidates_keccak is the hash of that file. A file that silently omitted in-window senders would still pass every check and still reproduce setRoot and N, while the omitted addresses were wrongly excluded. Completeness is the one property the header cannot bind.

So re-scan the windows yourself. They are exact block counts pinned in the header: Base (49,985,795 , 50,615,795] and Ethereum (25,761,306 , 25,862,106]. Membership is tx.from appearances in those blocks only — never nonce arithmetic, because post-Pectra an EIP-7702 authorization bumps a nonce with no transaction sent. The union, lowercased, deduplicated, sorted and LF-joined without a trailing newline, must equal candidates.txt byte for byte. Also confirm that B = 50,615,795 is the block carrying the token's deployment transaction: verify re-derives B from T_B but does not assert it is the genesis block, and the whitepaper's "B is not a chosen block" rests on that.

Steps 1–3 prove the rule was applied correctly to the published input. Step 4 proves the input was complete. Both together — not anyone's word — are the guarantee.

A note on the deployed source

The verified contract source keeps a few pre-deployment comments: WINNERS0 = 24_000; // provisional, two "finalize before deploy" items, and a // old 70% + 19.9% note from a superseded design. These are stale comments only. WINNERS0 is declared constant — fixed at deployment, unchangeable, and it is the value the odds above come from. The EIP-4788 semantics one note asked to confirm were confirmed by the seal itself: genesisSeed is non-zero. The contract is immutable, so the comments cannot be edited out.

What the rule was

All of, measured at B: held at least 0.1 ETH and strictly less than 40 ETH (Base and Ethereum balances combined) at both B and two weeks before B · first transaction at least 12 months before B, taking the earlier of the two chains · between 20 and 20,000 lifetime transactions across both chains · sent a transaction within the last ~two weeks · a plain wallet (no contract code, or an EIP-7702 delegation only). Thresholds are in ETH, so no price source or oracle is involved. The token, pool, vesting and founder addresses are excluded and named in the header.
